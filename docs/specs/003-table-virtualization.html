Table Virtualization and Expanded Bus Demo ​

1. Scope ​

Implement TanStack virtualization in the shared table and demonstrate it with more bus lines.

Delivered in PR #3. This specification supersedes the initial five-route demo size in 001-init.md.

2. Shared table virtualization ​

  • Use @tanstack/react-virtual with the existing shared TanStack Table renderer.
  • Make virtualization opt-in and enable it for the main bus schedule.
  • Keep short stops-dialog and design-system reference tables fully rendered.
  • Render viewport rows with two overscan rows on each side instead of mounting the entire dataset.
  • Measure row heights and the sticky-header offset.
  • Use stable table row IDs when scrolling, sorting and selecting.
  • Keep focused rows mounted so scrolling does not discard keyboard focus.
  • Expose the complete accessible row count, including headers, and logical aria-rowindex values on mounted rows.
  • Allow scrolling to the final row without clipping it.

3. Gantt lifecycle and preserved behavior ​

  • Mount Gantt components only for rendered rows.
  • Unmount offscreen Gantts and stop their live clock updates.
  • Continue live updates for mounted Gantts.
  • Preserve sorting, reset to input order, row selection and adjacent-column resizing.
  • Keep all geographic routes on the map regardless of which schedule rows are mounted.

4. Demo data ​

  • Expand the dataset to 30 distinct bus lines and 150 stops.
  • Keep route identifiers and row identities distinct.
  • Retain representative routes and schedules that demonstrate scrolling, sorting and selection.

5. Validation and delivery ​

  • Leave a runnable browser regression using the existing browser-check approach.
  • At a 1200x700 viewport, verify fewer mounted schedule/Gantt rows than the 30-row dataset.
  • Verify offscreen unmounting and stopped clock updates, continued visible-row updates, final-row reachability, sorting/reset, selection, resizing and keyboard-focus retention.
  • Verify that the map still contains all 30 routes.
  • Run existing design-system and transit tests, strict TypeScript checking and the production Pages-mode build.
  • Deliver on a feature branch through a pull request against main.
  • Publish to the GitHub Pages repository when requested; publication is separate from merging the application PR.
