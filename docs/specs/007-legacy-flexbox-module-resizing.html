Historical Specification: Flexbox Module Resizing ​

Status and precedence ​

  • Status: historical baseline for architectural research, not a request to restore this implementation.
  • Derived from the published historical guide.
  • Superseded for current pane resizing by Hybrid Grid Module Resizing.
  • The original walkthrough remains in the table documentation; its duplicate application-root file has been removed in favor of this specification.
  • Requirements below describe the historical contract. They must not be mixed into the current Grid implementation.

1. Scope ​

Resize adjacent application layout panels through the starterkit's existing recursive layout state and Flexbox sizing. Support native pointer and keyboard input without adding a splitter library.

Module-pane resizing is separate from table-column resizing and the editor's module/layout drag-and-drop.

2. Layout configuration and identity ​

  • LF-01: A resizable parent shall declare resizable.minPercent and resizable.maxPercent.
  • LF-02: Limits shall be finite and satisfy 0 < minPercent <= maxPercent < 100.
  • LF-03: The historical dashboard shall start with a 25:75 schedule/map split and allow a first-pane share of 25% through 75%.
  • LF-04: Resized siblings shall be layout-panel wrappers with stable UUIDs and positive finite flex-grow weights using a zero-basis sizing contract.
  • LF-05: Panels shall expose data-layout-id={uuid} for DOM lookup. Raw module siblings are not a supported replacement for these wrappers.
  • LF-06: Modules shall retain their existing container assignments and mount lifecycle.

3. Recursive rendering and state ownership ​

  • LF-07: For an enabled parent's layout.items, the renderer shall insert one separator between each adjacent pair without adding a wrapper DOM element. Three panels therefore have two separators.
  • LF-08: Separators shall remain presentation elements, not persisted layout nodes or entries in the editor tree.
  • LF-09: Each separator shall receive the parent, preceding panel, following panel, and parent UUID path.
  • LF-10: Child update paths shall include the root UUID and append the affected panel UUID. Traversal shall respect the existing layout service's root-relative conventions.
  • LF-11: Each handled movement or keyboard update shall commit the two affected flex styles through updateLayout, preserving existing node and style fields. Imperative width changes shall not replace authoritative layout updates.
  • LF-12: The implementation shall preserve the existing service's notifications. Consumers shall not assume atomic pair updates or a specific UPDATE_LAYOUT event: the historical service uses two calls and wildcard notifications.

4. Resize calculation ​

For adjacent weights a and b, starting coordinate c0, current coordinate c, and combined measured pane size S:

text
total = a + b
startPercent = a / total * 100
sign = -1 for a reverse flex direction, otherwise 1
requested = startPercent + (c - c0) / S * 100 * sign
bounded = min(maxPercent, max(minPercent, requested))
newA = total * bounded / 100
newB = total - newA
  • LF-13: Measure the two panes at pointer down and exclude separator space by using their combined dimensions.
  • LF-14: Preserve the adjacent pair's total weight and leave other sibling weights unchanged.
  • LF-15: Read orientation from the parent's configured inline flexDirection; use X for rows and Y for columns.
  • LF-16: Invert physical movement for row-reverse and column-reverse.
  • LF-17: Write normalized zero-basis flex shorthand, preserving unrelated style.

Historical parsing uses Number.parseFloat(style.flex) || 1. Missing, nonnumeric, or zero values become 1; negative values and arbitrary flex keywords are outside the supported contract. This is a recorded limitation, not a recommendation to weaken input validation in a new implementation.

5. Interaction and accessibility ​

  • LF-18: Only primary-button pointer input shall start resizing.
  • LF-19: The separator shall capture the pointer, prevent selection, and avoid triggering editor selection/drag behavior.
  • LF-20: Pointer up, pointer cancellation, and lost capture shall clear active drag state. There is no separate completion-only persistence step: movement has already updated shared layout state.
  • LF-21: Render a focusable separator with an accessible name, orientation, configured minimum/maximum, and current pair percentage.
  • LF-22: Applicable arrow keys shall change the first pane by two percentage points. Reverse flex directions shall invert physical arrow behavior.
  • LF-23: Home and End shall select the configured minimum and maximum.
  • LF-24: Use touch-action: none, an axis-appropriate resize cursor, a visible focus indicator, and nonselectable separator content.
  • LF-25: Allow panes to shrink with appropriate zero minimum width/height. Tables, maps, and canvases shall adapt to host size or scroll as intended.

Inherited RTL direction is not fully supported by this historical algorithm. Reverse-flex handling shall not be represented as complete RTL support.

6. Editor, persistence, and offline behavior ​

  • LF-26: Editor properties and separators shall operate on the same layout styles. Editing Flex shall affect the next interaction.
  • LF-27: Resizing shall remain available outside editor mode and in production. Existing permitted editor drop targets shall keep working.
  • LF-28: A full reload shall restore configuration defaults unless a destination separately implements persistence. This historical feature adds neither browser storage nor network preference requests.
  • LF-29: Porting shall reuse the destination's layout provider, state service, versions, and module boundaries rather than replace them.
  • LF-30: Air-gapped installation shall use authorized offline dependency artifacts without copying registry credentials. Offline builds shall not be represented as guaranteeing offline map tiles or external services.

8. Recorded limitations and non-goals ​

  • No animation-frame throttling or atomic pair update.
  • No dedicated simultaneous-pointer arbitration.
  • No automatic initial normalization of out-of-range imported weights.
  • No CSS-only orientation detection or complete inherited RTL support.
  • Geometry is assumed stable during a gesture.
  • Limits are pair percentages, not pixel minimums.
  • No built-in responsive breakpoint, preference persistence, undo, snapping, collapsing, or double-click reset.
  • Shared layout rerenders on movement can be expensive with heavy descendants.

These ceilings are part of the research baseline; they are not current feature requirements.
